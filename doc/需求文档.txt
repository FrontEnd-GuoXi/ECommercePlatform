轻量级电商交易与秒杀系统（FlashCommerce）需求规格说明书1. 项目概述与设计目标1.1 项目定位本项目旨在通过构建一个具备真实业务闭环的电商交易系统，帮助开发者打通从单体规范化 CRUD到高并发、分布式缓存、消息异步解耦及数据一致性保障的核心后端技术链路。1.2 核心演进目标业务闭环： 实现“商品浏览 $\to$ 购物车 $\to$ 下单锁定库存 $\to$ 超时自动关单/支付成功 $\to$ 库存结算”的完整电商链路。高并发秒杀： 支撑高并发读（商品详情与库存查询）与瞬时高并发写（秒杀抢购），杜绝超卖（Overselling）与少卖，保障数据最终一致性。工程规范： 统一 RESTful API 契约、全局异常拦截、防御性参数校验、基于状态机或严格枚举的业务状态流转。2. 核心业务流程2.1 常规交易流程[用户加购/立即购买] Trade)功能项需求描述关键技术规则购物车管理添加、编辑数量、移除商品、勾选结算。推荐基于 Redis Hash 结构存储（Key: cart:userId, Field: productId, Value: quantity），降低主库写压力。创建订单（常规）结算勾选商品，生成待支付订单。1. 幂等性保障：提交订单时前端携带从后端预获取的 #{qty}WHERE product_id = #{productId}   AND available_stock >= #{qty};检查受影响行数是否等于 1，若为 0 说明库存不足，业务回滚。秒杀库存扣减（Redis + Lua 原子性）：在 Redis 中使用 Lua 脚本保证“校验剩余库存 + 校验是否限购 1 件 + 扣减库存”在单次操作中原子执行，禁止通过在 Java 代码中分步调用 get 和 decr。分布式锁场景（Redisson）：当涉及到跨多资源聚合校验（例如：同一个用户不能同时触发两次结算扣款）时，通过 Redisson 对用户维度加锁（lockKey = "lock:order:create:" + userId），配置合理的租约时间与看门狗机制（Watchdog）。5.2 接口幂等性设计防重复下单 Token 机制： 进入确认订单页时，服务端下发一个唯一随机字符串 orderToken，以 orderToken 为 key 存入 Redis 并设置短期过期时间（如 5 分钟）。提交订单时，通过 Lua 脚本执行原子判断并删除：Luaif redis.call('get', KEYS[1]) == ARGV[1] then    return redis.call('del', KEYS[1])else    return 0end校验失败直接拦截，杜绝网络超时导致的重发问题。5.3 限流与容灾保护接口级限流： 秒杀抢购入口必须集成限流机制（使用 Sentinel 或基于 Redis 实现令牌桶/滑动窗口），设置阈值（如单 IP 每秒限制 5 次，系统总 QPS 阈值 2000）。超额流量直接返回提示信息：“排队人数过多，请稍后再试”。降级设计： 当秒杀商品详情访问激增时，页面渲染所需的部分非核心接口（如相关推荐、评论列表）实施自动熔断降级。6. 项目落地研发里程碑与任务清单阶段一：单体规范化基石（预计 1 周）[ ] 搭建 Spring Boot 项目骨架，统一响应体 Result<T> 及全局异常捕获器。[ ] 接入 Hibernate Validator 校验所有 Request DTO。[ ]
